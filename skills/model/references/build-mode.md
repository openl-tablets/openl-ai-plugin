# Build mode: list the inputs and turn them into datatypes

Part of the model skill, moved word for word from its SKILL.md. The Workflow, the hand-offs and Writing the table are in [SKILL.md](../SKILL.md); the full Non-negotiables are in [non-negotiables.md](non-negotiables.md); Scope and sources, the Workflow steps in detail and the Verification checklist are in [sources-workflow-verification.md](sources-workflow-verification.md); any other section named in parentheses is in one of the files listed under **Where to read** there. This file holds Workflow step 3 for build mode.

- *Build mode, step 1: list the inputs.* When no inventory and no user-provided model exist, build the inventory from the requirements. Go through every lookup or decision table, condition, formula and validation, and list each value it reads: the keys a table is looked up by, the operands of a formula, the values a rule's conditions test, and the identifier of each level. Classify each value. It is an **input** when the calculation needs it to run and no rule or table produces it; what the consumer actually sends is settled afterwards, when each input is matched to a source field. It is **calculated** when a rule produces it (it goes to the spreadsheet skill, not the model). It is a **decision table result** when a decision table returns it, such as a rate, a factor or an eligibility decision (it goes to the decision-table skill). Only inputs enter the input model. For each input, record the requirement that reads it, the object it describes (its level in the consumer's structure, for example a header or one of its line items), its type as the rule uses it (compared with ranges or used in arithmetic → number; matched against a fixed list → vocabulary; a date; yes/no → Boolean), and whether it repeats ("for each line" → an array). Ask for the raw value, not a derived one (the date or the amount, not the band it falls into), unless the consumer sends the derived value. For each input, find the field in the calling system's data that will supply it (its request, product model or integration mapping), so the consumer can map it: the claimant's age, for example, may come from a date of birth the calling system already holds. An input with no source field, or one the requirements leave unclear, goes on the clarification list. The result is the inventory: one row per input, with its requirement, owner object, type, cardinality and source field.
  Then generalise: inputs that are the same kind of thing become one object, not one field each. Twenty benefits, each with an amount, become an array of a `Benefit` datatype with a `benefitName` field (a vocabulary holding the twenty names) and a `benefitAmount` field. They do not become twenty `xxxAmount` fields on one object. A new item is then a new vocabulary value, not a model change, and the rules look it up by name instead of naming each field.
  Then settle each level and each list-shaped input with these questions; any that the requirements leave open goes on the clarification list:
  - *Cardinality and identifier.* Can the level repeat (several plans per policy, several coverages per plan)? If it might, ask, and don't default to a single object. Every major level gets an identifier (Non-negotiable 8).
  - *Selection flags.* When the requirements list items with a selected or included flag ("Selected? Y/N"), the default is that only selected items are sent: the flag is dropped, and being in the array means selected. Do not ask about it; state the default in the draft so the user can correct it. Keep the flag only when the consumer's data, the existing model or AGENTS.md shows that unselected items are sent too.
  - *Partial columns.* A column with values on only some rows (a yearly maximum that only some benefits have) is an optional field. Ask what it counts or measures, and name the field so it says so (`maxVisitsPerYear`, not `max`).
  - *Runtime context.* Inputs that match a runtime context property (state, effective or request date, LOB, country, currency, region) are candidates for rule versioning. Ask whether rules vary by them. Declare each confirmed one as a context field in the datatype (`state : context.usState`, or `field : context` when the field and context names match), using the format in the guide's *Runtime Context Properties in Datatype Tables*. The context variable has its own type (for `usState`, OpenL's US-states enum). Check in Studio that the field's type compiles as that context field; offline, list it among the things the user must check. Versioning by dates needs the rate effective date and the request date as context fields (`effectiveDate : context.currentDate`, `requestDate : context.requestDate`, both compiled in Studio); which dimensions and values to version by is decided with the versioning skill, and the request date is a new input only when the user agrees.
  A datatype field has two required columns, type and name. The other columns (default value, description, example, mandatory flag) are optional. Use the ones the siblings use; in a new project, propose them to the user. Suggest a value for each optional column, such as an example taken from the requirements or a sample request, and ask the user to confirm it or fill it in. Never invent a default.
- *Build mode, step 2: turn the list into datatypes.* Step 1 gives the list of inputs; this step writes it as `Datatype` tables. The top datatype is the entry point's single input, and nothing a rule computes goes in. Add the levels in the consumer's order, top-down: every level of the consumer's structure (or of the confirmed reference), including levels no input of step 1 lands on (Non-negotiable 11). Each row of the list becomes a field of its object, keeping the type, cardinality, required or optional, vocabulary and source field found in step 1, plus its default and the unit or meaning when it is not obvious. Add the vocabularies with their values from the source list. Fields that feed the runtime context are declared as context fields once the user confirms them (Runtime context, above).
