## Naming and layout


- **Table names.** Follow the siblings. Without a convention: the business name of what the table returns, in PascalCase (`AreaFactor`, `BaseRate`, `EligibilityDecision`), no type word such as `Table` or `Lookup` unless the siblings use one, no unexplained abbreviations. Unique across all modules, except versions of the same rule.
- **The business name is the requirement's term.** Name the returned value with the word the requirement, rate sheet or source workbook uses for it: a column headed "Adjustment Factor" gives `…AdjustmentFactor`. Never rename a value after its mathematical role or after how the calculation uses it (weight, share, multiplier, coefficient), even when the values sum to 1 or act as a weighted average. When the requirement has no term for it, propose a name and ask. Tables of the same kind in one group (the per-benefit schedule tables, the per-state factor tables) share one suffix, so the family reads as one: no mix of `…Weight`, `…Adjustment` and `…Factor` for the same kind of value.
- **Parameter names** are the names of the attributes they carry, as the model spells them (`areaCode`, `planType`).
- **Column titles** are business names taken from the requirement, in the siblings' style, with the unit where the value has one (`Rate per 1,000`, `Factor`).
- **Where tables live.** Follow the project's module structure. Where the project keeps them apart, decision tables live in their own (often versioned) lookups module, apart from the model and the calculation, one table per sheet, the sheet named after the table, so rows and columns can be inserted without touching another table. Related tables may share a sheet only where the project already does so, stacked and starting in the same column. When the project has no lookups module and the task adds many tables, ask before creating one, since module dependencies and versioning change with it. A new version of a table belongs to the versioning skill.
- **Sheet layout.** The module's Environment sheet is always the last sheet: a new sheet goes before it. The server cannot reorder sheets, so after adding a sheet, list the module's sheets; if the Environment sheet is no longer last, ask the user to move its tab to the end in Studio or Excel, and say so in the summary. A sheet left empty after its last table is removed is deleted, never the Environment sheet. List the module's sheets after a removal; if the server cannot delete the sheet, ask the user to delete the tab in Studio or Excel, and say so in the summary. Offline, remove the sheet from the workbook. One empty row and one empty column around every table. The header row is merged across the full table width; any properties rows sit directly under it. Notes go outside the table, separated by an empty column, never as an extra column inside it.
- **Formatting.** Fonts, fills, borders and number formats are optional and never block the task; do not ask the user to add them. The project's AGENTS.md or the user decides; otherwise:
    - *Through Studio:* write the cells only (the server can neither read nor set styles). If the user wants formatting, list the new tables and say it is done in Studio by copying a sibling table's look.
    - *Offline `.xlsx`:* copy the style of an existing table of the same kind on the sheet; with none, write plain cells; apply a house table format only when the user asks for it.
    - *Layout is not formatting* and always applies: the merged header, one blank row and column around each table, orientation, and the Environment sheet last.
