## Conditions and columns


Syntax (header format, column codes, range formats, escaping) is read from the bundled guide chapters. What this skill adds is how to use them:

- **Smart tables match by title.** OpenL splits each column title and each input name (and the fields of an object input) into words and links the column to the best-scoring input. Give each condition the business name closest to its attribute (`Area Code` for `areaCode`). When two inputs own a field with the same name, extend the titles with the owner (`Plan Type`, `Coverage Type`). After compiling, confirm every column matched the intended input: Studio shows the match on each title and warns about ambiguous matching. Return column titles of a compound return are matched to the fields of the return datatype the same way.
- **Rules tables: the short form.** When a condition only checks an input against the cell value, which is most conditions, write the input's name in the expression row and only the type in the parameter row: `coverageType` over `CoverageType[]` for a list of values in one cell, `rentOrOwn` over `RentOrOwn` for one value. OpenL generates the check itself: equality for a single value, "is in the list" for an array type. A return column (`RET1`) that returns the cell value needs neither expression nor parameter. Never hand-write `contains(...)` or `==` with named parameters for a plain match: that is what the engine already does. Write an explicit expression only for a check the short form cannot express (a comparison between two inputs, a calculation), and prefer an `Is True?` column in a Smart table for it. In a Rules lookup, the code row holds `C1 … | HC1 … | RET1`, and the title row holds the vertical titles followed by the horizontal values (`Coverage Type | Own | Rent`). See Example 5 in the worked examples.
- **Simple tables match by position.** The first condition column is the first input, and so on; the number and order of inputs equal the conditions. Titles are free text but still business names.
- **Lookup layout: prefer horizontal conditions, keep a balance.** Start from the layout with one vertical key, the one with the most or the longest values (usually the coverage, the plan or the long band list), and every other key across the top, stacked: the key with fewer values or a coarser grouping on the upper row, merged over the columns it groups, and the finer key on the row below (`0 - 10` merged over `Own | Rent`). Then check the balance. A table that needs horizontal scrolling, or whose columns become too narrow to read, moves its least readable horizontal key back down the rows; a table that repeats the same group of rows over and over moves a key up. The aim is a grid a person reads at one glance, wider rather than longer when both fit. Count the shapes (rows × value columns) of the candidate layouts and show the chosen one in the reply. See Example 6 in the worked examples.
- **Values that read by themselves go across the top; bare codes need a title.** Keys whose values are clear at a glance (Male / Female, Accident / Sickness, Own / Rent, and also ages, bands and zip ranges) read well across the top without a title. Bare numbers whose meaning is not obvious (a waiting period of 0 / 7 / 14, a benefit period of 3 / 6 / 12) need a visible title: put them down the rows, where every vertical condition has its title cell, or give the horizontal conditions titles. When two such keys would sit on top of each other untitled, swap one of them with a readable vertical key. Horizontal titles go in the last vertical condition's column, one per horizontal header row: the upper rows hold the horizontal titles alone (`Gender`, `Benefit Period`), and the last header row holds the vertical title, a slash and the last horizontal title (`Age / Coverage Type`); the other vertical titles stay merged down over all header rows. This form compiled in Studio. The guide also shows a separate title column after the vertical conditions, but with one empty cell per body row Studio read it as horizontal values and failed; in the guide's picture its body is one merged empty block, so use it only after a compile check. See Example 7 in the worked examples.
- **In a SimpleLookup the signature fixes the layout.** It matches inputs by position: the vertical conditions are the first parameters and the horizontal ones the rest, in order, and it has no horizontal titles. When the readable layout needs another split, change it to a SmartLookup with titled horizontal conditions, which keeps the signature, and say so in the reply. Reordering the parameters instead is a signature change (Non-negotiable 6).
- **Lookup headers.** The title cell of each vertical condition is merged down over all the horizontal header rows; the horizontal header rows hold values only. Several horizontal conditions are stacked rows, the upper one merged across the columns it groups. Titles for the horizontal conditions go after a slash in the last vertical title (`Rated Age / Gender`) or in a separate title column. Follow the siblings; where there is no precedent, give the horizontal conditions titles (Choosing the table type).
- **Ranges.** One cell per band, both ends included, in the project's notation (Non-negotiable 5). Some range texts look like dates or formulas to Excel (`1-4`, `=5`): they are written as text, never as numbers or dates. Two merged condition columns holding a minimum and a maximum are a different notation, read as minimum included and maximum excluded; use them only where the siblings already do. String ranges (`A100 - A999`) compare as text, not as numbers: `A1048` already falls inside `A100 - A999`, and `A20` falls after `A100`. Point this out when the requirement seems to mean numbers. The guide lists string ranges for SmartRules tables; in any other table type, a string range needs a compile check before it is trusted.
- **An array input is not a "contains" match.** A Smart table whose parameter is an array (`OtherPolicyType[] otherPolicyTypes`) and whose condition cells hold single values compiles, but matched only a one-element array in Studio (`[Home]` matched `Home`; `[Home, Home, MotorcycleSnowmobileATV]` matched no row). For a value per element, keep the parameter singular and let the caller pass the array, which runs the table once per element (rule applied to an array); the caller removes duplicates first when each distinct value counts once (spreadsheet skill). A Rules table with an array type in the parameter row checks "is in the list" the other way round: the input is single and the cell holds the list.
- **Several values, one row — only as the requirement has it.** A comma-separated list in one cell is used only where the requirement groups the values in one line, or the user asks; otherwise each value keeps its own row (Workflow step 2). A comma inside a single value is escaped as `\,`, otherwise the value is split in two.
- **Merged cells.** Identical adjacent condition or return values may be merged to show a group; OpenL unmerges them, so every row is still a full rule. Merging is for readability only and never changes which row matches.
- **Blank means any; first match wins.** A blank condition cell is always true. Rows are checked top-down and the first full match returns (Non-negotiable 4). A filled condition cell does not match an empty input, so an empty input falls through to the catch-all row or to no match; no match returns null (unless the table raises an error instead), and a null factor silently empties a product further up. When an empty input must return something different from other unlisted values, ask, and express it with a condition the guide supports, such as an `Is True?` column.
- **A blank return cell is not "nothing".** The engine skips that row and keeps looking for the next matching row with a value. Never leave a return cell blank to mean null or zero; write the value the user gives.
- **Return columns.** One return column is the norm. A SmartRules table may have up to three return columns: the first non-empty one is returned, so they are a fallback chain, not three results. To return all matching rows use `Collect`; to return several values of one match use a compound return. Return cells hold the return type; a cell that calls another table needs that table to return the same type.
- **Formulas in cells.** A cell starting with `= ` is an expression: a return cell may compute from the inputs or call another table (`= BaseRate (planType) * adjustmentFactor`). Keep a number literal when the requirement gives a number, and a formula with the given figures when it gives a rule (Non-negotiable 9). Read a field bare when only one input owns it: `= subBenefitAmount * …`, not `= subBenefit.subBenefitAmount * …`; keep the owner only when two inputs (or an input and an array of the same type) have a field of that name. A vocabulary value inside a formula (`"SecondDegree"`) goes to a parameter typed by that vocabulary, never to a `String` parameter, so a misspelled or renamed value fails to compile instead of matching nothing. A condition that is an expression goes in an `Is True?` column or an external Conditions table, never in a value cell of an ordinary condition.

## Completeness and conflicts


A table is complete when every input it can receive matches the row someone decided on, and unambiguous when no input matches two rows that disagree.

- **The value domain of each condition.** A vocabulary input: every vocabulary value. A `Boolean`: true and false. A number: from the lowest to the highest value it can take, with open bands at both ends where the model allows them. A free string with no vocabulary: the domain is unknown, so ask, or agree a catch-all. And for an optional input without a vocabulary: empty. A value the caller calculates (not in the model): no model domain. Read the step that computes it for the values or range it can produce; when that does not settle it, ask, or agree a catch-all. Never invent its bounds.
- **Combinations.** With several conditions the domain is their combinations. A lookup grid covers each combination of its two keys in one cell; an empty cell in the grid is skipped, not zero, so it is a gap to ask about.
- **Gaps.** A value the input can take that no row covers, so the table returns nothing for it: an age of 27 when the bands are `18 - 25` and `30 - 39`, or a vocabulary value no row lists and no catch-all catches. List each gap and ask the user what it returns (Non-negotiable 3).
- **Overlaps and unreachable rows.** Two rows that match the same input: the lower one never wins for that input. A row below a catch-all, a duplicate row, or a band fully inside an earlier band is unreachable. Report each with the rows involved; fix it only with the user's agreement, because the intended rule may be either row.
- **The temporary gap and overlap check.** OpenL can warn about gaps and overlaps through a decision-table validation property (read its name and values in the *Dev Properties* chapter). Set it on the new or changed table on the branch, compile, read the warnings, then remove the property before the change goes for approval; it never stays in the saved table. It reasons only about conditions with a known value set, so the domain run below is still needed.
- **The domain run.** Run the table on every vocabulary value, on the lower and upper boundary of each band plus one value inside it, on one value below the lowest band and one above the highest, and on an empty input. For a calculated input, use the values its computing step can produce, or the ones the user agreed. Compare each result with the requirement.
