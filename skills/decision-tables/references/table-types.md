## Choosing the table type


A decision table picks a value by conditions on its inputs. Choose the type by the shape of the requirement, and use the type the siblings use when they settle it:


- **One or more keys read down the rows, one value back → SmartRules.** The default. Conditions are matched to inputs by column title, inputs may be whole objects, and a condition may be a boolean expression (a column titled `Is True?`). Most factor, rate, eligibility and decision tables are SmartRules.
- **A value at the crossing of two or more keys → SmartLookup.** Horizontal conditions are preferred: every key that reads well across (gender, tier, plan, own/rent, a year, a duration, and also bands and ranges such as `0 - 10` or `A100 - A999`) goes across the top, several of them stacked when that stays readable, and only the key with the most or the longest values goes down the rows. Balance the width against the height (Lookup layout). A requirement table with columns and columns of conditions and one number per combination is usually a lookup. Horizontal conditions are matched to inputs in one of two ways. If they have titles (after a slash in the last vertical title, or in a separate title column), each title is matched the same way a vertical title is, so it can name an attribute of an input object. If they have no titles, they take the inputs left after the vertical conditions are matched, in signature order, so those inputs must be plain values listed in the same order as the header rows. Follow the sibling tables. Where there is no precedent, give the horizontal conditions titles, because the table then does not depend on parameter order.
- **SimpleRules / SimpleLookup only when the siblings use them.** They match inputs by position: every input is a condition, in the same order, and nothing else can be passed. A Smart table does everything they do.
- **A check or a result plain columns cannot express → an external Conditions or Returns table,** which a Smart table uses through its column titles. Use one for a non-plain check needed in several tables, or a result built from several cells. Before writing or changing one, read [references/external-and-rules-tables.md](external-and-rules-tables.md). It covers when one is needed, what goes in its Inputs, Expression, Parameter and Title rows, and how to tell a condition from a return.
- **Rules (with column codes) only when nothing else fits**, or when the task or the siblings ask for it. For example an action column, a list of values returned per rule, or a condition no `Is True?` column and no external Conditions table can express. Check those two first; they keep the table a Smart table. A Rules table can also be a lookup: horizontal conditions (`HC1`, `HC2` …) put a short key across the top. Write it in its short form (Conditions and columns); its full column declarations are in [references/external-and-rules-tables.md](external-and-rules-tables.md), section 5.
- **Separate requirement tables stay separate tables, with one routing rule.** When the requirement gives a separate table per value of a key (a rate or incidence table per benefit, an increased limit factor table per coverage, a factor table per plan), build one table per requirement table, in the requirement's own layout, and one small SmartRules routing table keyed by that value whose return cells call the per-key tables (`SmartRules Double IncreasedLimitFactor (Coverage coverage)`: `Coverage Type | Rule for Increased Limit Factor`, rows `BodilyInjury | = BodilyInjury (limit)`, `Comprehensive | = Comprehensive (deductible)` …). This holds whether the tables read the same inputs or different ones. Never merge them into one large table with the key as one more condition: a merged table is hard to read and to check against the requirement, while separate tables can be compared with their source one by one, updated and versioned on their own. The routing table takes the owning object or the key plus the shared inputs, so the caller makes one call and does not need to know which table each key reads. Keep a per-key table even when two keys share the same values today, unless the user says they always move together. Merge only when the requirement itself is one table, or when the user asks. See Examples 8 and 9 in the worked examples.
- **Several values back for one match → one table with a compound return** (a datatype return whose fields are matched by the return column titles), when the values share the same keys and are always read together. **All matching rows back → `Collect`** with an array return type.
- **A list of allowed values → the vocabulary in the model.** This skill reads vocabularies as the value domain of a condition; it never adds, removes or renames their values (Workflow step 1).
- **A calculation → a Spreadsheet, not a decision table.** When the logic is a sequence of steps that build on each other, or a return cell would hold a long formula, use the skill that builds Spreadsheet tables. The reverse also holds: a ternary nested deeper than two or three branches in a spreadsheet step becomes a SmartRules table that the step calls.

One table holds one business factor or decision. Two requirement tables with the same keys that are always read together may become one table with a compound return or one lookup; propose it, because it changes the signature for every caller (Non-negotiable 6).
